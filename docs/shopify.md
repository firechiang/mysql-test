# 我们用 MySQL 替代 Redis 实现库存预留——并成功扛住了高并发

> **副标题：** 我们如何利用 `SKIP LOCKED`、复合主键与连接可观测性达成规模化目标。  
> **更新时间：** 2026 年 5 月 12 日  
> **作者：** [Emilie Noel](https://shopify.engineering/scaling-inventory-reservations)（Shopify Engineering）

---

在结算过程中，当买家点击“完成购买”时，系统必须确保他们选购的商品依然有库存。如果在一个方向上出错，两位买家同时拍下最后一件商品，商家就必须取消订单、发送道歉邮件并承担售后客服成本；如果朝另一个方向出错，系统向买家误报售罄，商家则会白白损失本可达成的销售额。

在 Shopify 的体量下，任何一种失误都会被迅速放大。在 2025 年黑五（Black Friday）期间，平台商家的峰值交易额达到了创纪录的每分钟 510 万美元，其中每一笔交易都会触及库存。

Shopify 的**防超卖系统（Oversell Protection System）**通过在支付处理期间预留库存来解决这一问题——这是一种短暂的锁定，防止两次并发的结账操作抢占同一件商品。多年来，这套逻辑一直运行在 Redis 上。而当我们推行统一数据库策略时，面临一个严峻问题：**MySQL 能够承载同等规模的流量吗？**

早期的尝试均告失败，因为采用“单行记录配合数量列”的方案无法承受剧烈的锁竞争。但 MySQL 8 的 `SKIP LOCKED` 特性带来了一种全新设计：**单件商品单行记录（One row per unit），而非按品类单行（One row per item）**。受 [37signals 基于数据库实现负载分发方案](https://37signals.com) 的启发，我们在 MySQL 上重构了预留系统，并在 2025 年高峰流量期间成功达成了高吞吐量目标。

然而，最艰巨的教训并非来自数据库设计本身，而是发现**真正的瓶颈并不在原先监控和度量的指标上**。以下为完整的解决方案与落地过程中的发现。

---

## 面临的挑战

### 什么是防超卖机制？

防超卖机制包含两项核心操作：
* **预留（Reserve）：** 支付开始时将商品标记为预留状态（短期锁定，如数分钟）。
* **核销（Claim）：** 支付成功后，从库存总账（真实真值源，Source of Truth）中永久扣减库存数量。

结账完成链路严重依赖该过程的快速与准确。缓慢的预留操作会引发流控并恶化买家体验；而错误则意味着超卖（引发客诉）或少卖（损失营收）。

### 规模与正确性要求

此处的业务体量绝非抽象概念：Shopify 承载了美国电商超过 14% 的交易份额，且在 2025 年黑五期间，峰值销售额同比前一年提升了 11%。由于所有涉及库存的结账都会触发预留，系统必须在承受流量突增的同时，不发生请求丢弃或一致性破坏。

核心技术诉求包括：
* 支撑平台高峰流量期的高吞吐性能目标。
* 支持多仓库库存（Multi-location inventory，仅从能履约的仓位进行预留）。
* 在预留与库存总账之间保持 ACID 事务保证。
* 正确性优先：严禁超卖，严禁预留数据丢失。

### Redis 架构及其瓶颈

原系统将预留状态存放在 Redis 中。每个商品维护一个数量键，预留执行 `DECR`，释放执行 `INCR`。Redis 处理并发性能优秀，但**预留系统与库存总账位于两个独立的系统中**。

核销环节（支付处理完毕、永久扣减库存）必须同时执行更新 MySQL 与清理 Redis，而这两步操作无法封装在单次原子事务中。根据执行顺序的不同，可能产生两类异常：
* **超卖：** 商品售出但从未在总账中扣减。
* **少卖：** 商品在总账中被扣除，但在 Redis 中仍显示为被预留。

此外，Redis 模型难以感知多地点库存逻辑，且额外增加了独立集群的运维成本。将预留逻辑迁移至同一 MySQL 数据库后，所有操作均可通过 ACID 事务包装，彻底消除了此类异常场景。

## 解决方案：SKIP LOCKED

### 核心思想：单件单行，设定容量边界

不再使用“单商品对应单行+数量列”的结构，而是**每个可售单元占用一行独立记录**。若某商品有 10 件库存，表中即有 10 行记录。预留 3 件意味着在单个事务中选出并转移 3 行数据。预留与库存总账同处一个数据库，实现了跨预留与核销的全局 ACID。

简化后的预留事务逻辑如下：

```sql
-- 使用 READ COMMITTED 隔离级别启动事务
BEGIN;

-- 挑选 N 个可用单元，跳过被其他事务锁定的行
SELECT id
FROM available_units
WHERE shop_id = ?
  AND inventory_item_id = ?
  AND inventory_group_id = ?
ORDER BY shop_id ASC, inventory_item_id ASC, inventory_group_id ASC, id ASC
LIMIT 3
FOR UPDATE SKIP LOCKED;

-- 将选中的记录移入预留表 reserved_units
INSERT INTO reserved_units (unit_id, cart_token, expires_at, ...) VALUES (...);

-- 从可用库存池中移除
DELETE FROM available_units
WHERE (shop_id, inventory_item_id, inventory_group_id, id) IN (?, ?, ?, ?);

COMMIT;
```
SKIP LOCKED 是达成高并发扩展的关键：若某些记录已被其他事务持有排他锁，MySQL 会自动跳过并直接返回其他空闲行，避免线程在同一行记录上等待，大幅消除了锁竞争。

### 1,000 上限缓冲池设计：
若为全量库存都生成单行记录，当商品在 10 个仓库拥有 50,000 件库存时，单表需维护 500,000 行，执行扫描预留查询会显著变慢。因此，系统为每组“商品/仓库”组合维护一个最多 1,000 行的有界可用缓冲池（Bounded Pool）。预留操作消耗池内记录，后台补充程序负责从库存总账向池内回填记录。
* **为什么设定为 1,000？**
* 容积足够大：足以吸收瞬间抢购峰值而不至于过快耗尽。
* 表结构足够紧凑：确保 SKIP LOCKED 扫描维持极低延迟。
* 该数值基于闪购期间观测到的单点单品峰值消耗速率制定。

* **池耗尽如何处理？**
* 极端闪购下若缓冲池耗尽，预留链路会同步触发补充逻辑。
* 引入锁保证同一商品同一时间仅有一个事务执行补充，其余并发预留排队等待其完成，避免惊群效应（Thundering Herd）。
* 补充完成后排队事务基于填满的池继续处理，买家不会被误判缺货，在稍增单次延迟的同时严格保障了业务正确性。

### 关键技术决策
#### 1. 复合主键：减少单行持锁数量
最初的原型使用自增 ID 作为主键。通过 SHOW ENGINE INNODB STATUS 观测锁状态时，发现每次预留会产生 2 把行锁：InnoDB 既锁定了 WHERE 条件命中的二级索引，又锁定了主键聚簇索引。

团队将其改造为复合主键 (shop_id, inventory_item_id, inventory_group_id, id)，使过滤字段本身成为主键的一部分。此举将每次预留的锁持有缩减为 1 把行锁，显著提升了高并发下的吞吐上限。

#### 2. READ COMMITTED：杜绝间隙锁与伪记录锁
在空表或需补充库存的状态下执行 SELECT ... FOR UPDATE SKIP LOCKED 时，默认的 REPEATABLE READ 隔离级别会引入间隙锁（Gap Lock）以及针对上界伪记录（Supremum Pseudo-record）的锁定。这些锁会阻塞补充事务的 INSERT 动作，进而引发死锁。

团队将该业务事务的隔离级别调整为 READ COMMITTED。在该级别下，InnoDB 不会以相同方式加间隙锁，补充事务得以并发插入新记录。

#### 3. 统一加锁顺序：彻底消除死锁环路
早期测试中，预留（Reserve）与核销（Claim）以不同顺序操作表结构导致了死锁：预留先向 reserved_quantities 插入数据再从 reservation_units 执行删除，而核销直接从 reserved_quantities 删除，不同事务以交叉顺序锁表产生循环等待。

修复方案是规范全链路加锁顺序：
* 预留链路固定先从单元表执行 DELETE，再向预留表执行 INSERT。
* 核销链路仅操作预留表。
* 双方以统一严格的顺序申请锁，杜绝了成环可能。

#### 4. 批量查询：使用 UNION ALL 缩减往返时延  
跨网络与数据库交互存在固定往返成本。针对购物车中多品类合并结算的场景，系统采用 UNION ALL 将多条子查询合并在单次请求中往返：
```sql
( SELECT id, inventory_item_id, inventory_group_id
  FROM available_units
  WHERE shop_id = 1 AND inventory_item_id = 100 AND inventory_group_id = 1
  ORDER BY shop_id, inventory_item_id, inventory_group_id, id
  LIMIT 2 FOR UPDATE SKIP LOCKED)
UNION ALL
( SELECT id, inventory_item_id, inventory_group_id
  FROM available_units
  WHERE shop_id = 1 AND inventory_item_id = 200 AND inventory_group_id = 1
  ORDER BY shop_id, inventory_item_id, inventory_group_id, id
  LIMIT 5 FOR UPDATE SKIP LOCKED)
```
该方式大幅降低了数据库连接的总往返次数，改善了高负载时的请求延迟。

### 真正瓶颈：数据库连接，而非 CPU
在生产级压测中，吞吐量在远低于预期目标处遭遇瓶颈。然而预留本身的 P90 延迟表现良好，数据库 CPU 远未跑满，查询本身也已深度调优。

#### 追踪真实症状
压测过程中表现出的异常征兆
* MySQL 内部线程排队积压。
* 排队任务集中触发时引发 CPU 突刺。
* ProxySQL 代理层对 MySQL 后端连接彻底耗尽。

系统缺乏“究竟是哪个业务过程在持有连接、持有了多久”的可观测性。仅获知连接耗尽无法反推资源持有源头。

团队实施了链路级归因方案：
* **应用层注入标签：** 在每条 SQL 中注入包含业务名称的注释（例如 /* conn_tag:checkout_completion */）。
* **代理层统计聚合：** ProxySQL 解析该注释标签，并统计各业务调用方持有连接的时间开销，生成按业务划分的总连接持有时间分布。

#### 归因定位与优化

通过指标归因发现，预留并非唯一的连接占用大户，结账主路径上的其他遗留代码长期持有连接未及时归还。这些代码因为此前并未触碰上限而从未被优化。在高并发场景下，系统需要海量的“短平快”事务，其他长连接事务耗尽了连接池容量，库存预留成了压垮骆驼的最后一根稻草。

随之采取的整改措施：
* **清理主路径无效开销：** 优化结账路径，使数据库主库读取量降低 50%，事务总量降低 33%。
* **调整底层并发参数：** 调高了多年前保守配置且从未复核过的 innodb_thread_concurrency 参数，释放硬件潜能。
* **成果表现：** 瓶颈彻底解除，高流量闪购测试中主写库 CPU 维持在 50% 以下，读库 CPU 维持在 16% 以下，保有充裕冗余度。

### 切换与灰度方案（Shadow Mode）
系统未采用直接关停切换的方式，而是启用了影子模式（Shadow Mode）双轨运行：

* **双写与校对：** 每一笔预留请求同时写入 Redis 与 MySQL，期间 Redis 始终充当真值源。通过对比二者在真实生产流量下的业务表现，验证 MySQL 的正确性与性能。由于两套系统实时在线，切换时无需迁移飞行中（In-flight）的预留数据。
* **快速回滚保护：** 判定无误后将真值源切至 MySQL；一旦发现任何异常，可借由熔断开关瞬间切回 Redis（双写通道维持开启，保证 Redis 拥有完整的全局预留视图）。
* **渐进发布：** 按照独立集群 Pod 逐步放量，由低流量 Pod 稳步灰度推进至全平台交易量顶尖的超级商家。

### 核心经验总结
#### 1. 重新审视历史假设
五年前 MySQL 无法胜任的业务场景，在 SKIP LOCKED 等新特性支持下已完全可行。配置项亦然：随着负载和硬件迭代，必须定期重新检视既往经验法则配置。若指标反常（如低 CPU 伴随高排队），必须深入探究底细。
#### 2. 小处着手，重视观测
脱离复杂框架、基于极简 Ruby 脚本与 MySQL 原型进行调试带来了巨大收益。在终端实时观测锁行为（如 SHOW ENGINE INNODB STATUS）比纯理论推导有效得多。当技术选型倾向于引入 Redis、Kafka 或自研协调层来处理高吞吐互斥时，既有关系型数据库往往已具备胜任能力。

瓶颈往往不在预期之处：团队花费数周调优 SQL 与行锁，但制约上限的实质是未受关注的代码对连接的隐形占有。预留系统必须成为数据库内“友善的邻居”，避免拖垮同库运行的购物车、支付与订单链路。
